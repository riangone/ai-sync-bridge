Problem & Approach

課題と本基盤の方針

SECTION 01
!
改修できない

長年稼働している基幹システムは、改修や検証の負担が大きい。ソースや設計書が揃っていない場合もある。

!
権限を守れない

文書をまとめて検索対象にすると、本来見られないデータまで AI 経由で見えてしまう。

!
説明できない

AI がどのデータを根拠に回答したのか、後から確認できない。

✓
本基盤の方針
  • 読み取りのみ: Connector は HTTP 一覧の取得、SQL の SELECT、ファイル読み込みだけを行う
  • 差分同期: 内容が変わった行だけ再埋め込みし、埋め込みと同期位置を永続化する
  • 権限の事前適用: 閲覧できない文書は、スコア計算にも LLM へのプロンプトにも入れない
  • 監査: 同期・検索・AI回答をハッシュチェーンで記録する

Retrieval

検索の仕組み

SECTION 04
H
ハイブリッド検索
  • 文字 bigram の BM25 とベクトル検索を RRF で統合する
  • BM25 の統計は閲覧可能な文書だけで計算し、隠れた文書の存在を推測されないようにする
  • 簡易ハッシュの埋め込みではベクトルの重みを下げ、関連度の低い文書を除外する
  • 件数・重み・足切りは bridge.yaml で変更できる
V
ベクトルバックエンド
層方式このサーバーの状態
sqlite-vecネイティブ拡張読み込めない(32 ビット形式の配布物)
ANNランダム射影動作する
brute-force全件のコサイン計算公開デモの既定

外部通信なしの埋め込みは簡易ハッシュで、意味の近さは判定しません。意味検索には実モデルの接続が必要で、精度の定量評価はまだ行っていません。

Incremental Sync

SECTION 05
S
処理の流れ
# 同期の流れ(実装: app/bridge/sync_engine.py の要約) for row in connector.fetch_changes(entity, cursor): content_hash = sha256(本文 + ACL) if 保存済みのハッシュと埋め込みモデル ID が同じ: continue # 再埋め込みしない 保存(row, embed(本文), content_hash) 監査ログ("sync.upsert") カーソルを保存 # 再起動後は続きから

操作埋め込み回数
初回同期文書数と同じ
変更なしで再同期0 回

  • 同期は手動または interval_sec による定期実行

RAG
AI 回答の規則
  • LLM に渡すのは権限内の文書だけ
  • 該当する文書がなければ LLM を呼ばず定型文を返す
  • 会話履歴は「テナント + 利用者 + セッション」で分離
  • 回答中の引用番号を照合し、一致しない番号を除去
  • 文書はデータとして区切って渡す(プロンプトインジェクション対策の第一層で、完全な防御ではない)
  • 実 LLM(antigravity)では ERP デモの1問で確認した。回答精度の評価ではない

種別内容

確認できることと限界
  • 各レコードは前レコードのハッシュと連結し、途中の書き換えや削除を検証 API で検出する

  • 端末や画面の記録、SIEM 連携は未実装
