AI-Sync Bridge 概要仕様書

既存の業務システムを改修せず、権限と監査を保ったまま AI 検索・AI 回答を追加する連携基盤

2026年11月4日時点の実装に基づく。実測値の条件は第7章、未実装の項目は第8章に記載。

1. 解決する課題

基幹システムのデータを AI から使いたくても、次の理由で進まないことがあります。

  • 改修できない: 長年稼働している基幹システムは、改修や検証の負担が大きい。
  • 権限を守れない: 文書をまとめて検索対象にすると、本来見られないデータまで AI 経由で見えてしまう。
  • 説明できない: AI がどのデータを根拠に回答したのか、後から確認できない。

本基盤は、既存システムからデータを読み取るだけで取り込み、利用者の権限内のデータだけで検索・回答し、その経緯を監査ログに残します。

4. 権限制御(ACL)

権限判定は検索の前に行います。閲覧できない文書は、スコア計算にも LLM へのプロンプトにも入りません。BM25 の統計も閲覧可能な文書だけで計算するため、スコアの変化から隠れた文書の存在を推測されることを防いでいます。

5. AI 回答(権限内 RAG)

  1. LLM に渡すのは、権限フィルタを通過した文書だけです。
  2. 閲覧できる文書が1件もなければ LLM を呼ばず、定型文を返します。
  3. 会話履歴は「テナント + 利用者 + セッション」単位で分離します。
  4. 回答中の引用番号を実際に渡した文書と照合し、一致しない番号は除去します。
  5. 回答ごとに、元の検索・使用文書・引用・回答本文を監査ログに記録します。

LLM にはツール実行権限を与えません。文書本文はデータとして区切って渡し、文書内の命令に従わないよう指示しています。

6. 監査ログ

種別記録内容
sync.upsert / sync.delete取り込み・削除した行と内容ハッシュ
sync.run同期ごとの件数・所要時間・エラー
retrieval利用者、検索語、渡した文書(内容ハッシュ付き)、権限で除外した件数
rag.answer関連する検索、使用文書、引用、回答本文

各レコードは sha256(前レコードのハッシュ + 本体) で連結され、途中の書き換えや削除は検証 API で検出できます。検索語と回答本文を残すかどうかは設定で変更できます。

7. 実測値

条件: 本デモサーバー(aarch64, 2 vCPU, 12 GB RAM)、合成 CSV データ、ハイブリッド検索 ON、top_k=5、60クエリを逐次実行、全文書が閲覧可能な利用者。埋め込みは外部通信のない 64 次元 n-gram ハッシュのため、OpenAI 等の埋め込み API を使う場合、初回同期はこの値より大幅に長くなります。

文書数初回同期1行変更の同期再起動時の読込検索 p50検索 p95最大メモリ
1,0000.19 秒0.05 秒0.05 秒16 ms17 ms73 MB
10,0002.0 秒0.54 秒0.62 秒146 ms160 ms183 MB
50,00010.9 秒2.8 秒3.5 秒767 ms846 ms673 MB
  • 埋め込み回数: 全規模で、変更なしの同期は 0 回、1行変更は 1 回、再起動は 0 回でした。
  • 検索時間: 文書数にほぼ比例します。BM25 が閲覧可能な全文書を走査するためで、ベクトルバックエンドを変えても 10,000 件での差はほとんどありませんでした。
  • 稼働中の ERP デモ: 同期対象は百数十件、API プロセスのメモリは約 81 MB です。
現状で実用的に応答できる目安は1万件程度までです。それを超える規模では、BM25 の転置インデックス化が必要です。

9. PoC の進め方(目安)

時期実施内容完了条件
第1週対象データの選定、読み取り専用の接続確認、権限表の整理取り込み対象と権限の対応が確定
第2週プロファイル作成、初回同期、差分同期の確認変更行だけが更新される
第3週LLM の接続、利用者ごとの検索・回答の確認権限外データが回答に出ない
第4週現場での試用、精度と応答時間の計測、監査ログの確認本番化の可否と追加開発の範囲を判断

接続先の環境やデータ規模により期間は変わります。第8章の項目が要件に含まれる場合は、別途開発期間が必要です。
